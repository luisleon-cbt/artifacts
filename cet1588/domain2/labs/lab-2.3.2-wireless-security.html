A password isn't enough.

A single shared Wi-Fi password (a pre-shared key) works for a home, but it falls apart in an organization: everyone uses the same secret, so when one person leaves you must change it for everyone, and a leaked key compromises the whole network. The enterprise answer is per-user authentication — each staff member logs in with their own credentials, validated by a central RADIUS server. In this lab you'll upgrade the Staff network to WPA2-Enterprise backed by a RADIUS server, stand up a separate Guest network on its own VLAN, and learn how WPA3 and captive portals fit in — the security half of the wireless exam objective.

Two kinds of "who are you?"

Every secured Wi-Fi network answers one question before letting a device on: how do I know you're allowed here? There are two fundamentally different answers, and the Network+ exam wants you to know both cold. Pre-shared key (PSK) uses one shared password for everyone. Enterprise gives every user their own credentials, checked against a central authentication server using the 802.1X framework and a RADIUS server. This lab builds the enterprise model for staff and keeps a simpler model for guests — exactly how a real organization separates trusted employees from visitors.

Network+ Context — Read this first

The Network+ N10-009 exam is vendor-neutral. You will not type Cisco commands on test day. Packet Tracer is used here because it can actually run a RADIUS server and authenticate a wireless client against it — letting you watch enterprise authentication work end to end. The concepts the exam tests — WPA2 vs WPA3, PSK vs Enterprise, the role of 802.1X and RADIUS, guest networks, and captive portals — are vendor-neutral. Focus on what each piece does and why, not on any product's menus.

The three players in 802.1X

Enterprise authentication has three roles. The supplicant is the client device asking to join. The authenticator is the AP (or switch) that relays the request — it blocks all traffic until authentication succeeds. The authentication server is the RADIUS server that actually checks the credentials and says yes or no. Memorize these three terms — the exam loves to ask which device plays which role.

Never WEP, never WPA (original)

Older standards WEP and the original WPA are both broken and must never be used. If the exam offers WEP or WPA as an answer for "most secure," it is wrong. The acceptable answers today are WPA2 (still widely deployed) and WPA3 (preferred). Know the chronological/security order: WEP < WPA < WPA2 < WPA3.

Guest networks & captive portals

A guest network is a separate SSID, on a separate VLAN, that gives visitors internet access without touching internal resources. It's isolated from the corporate VLANs (the red boundary above) — guests can reach the internet but not staff servers, printers, or files. A captive portal is the web page that intercepts a guest's first connection attempt and forces them to do something — accept terms of use, enter an email, pay, or log in — before internet access is granted. You've seen these at hotels, airports, and coffee shops.

Success Criteria

By the end of this lab you must demonstrate:

  1. A RADIUS/AAA server added, with the AAA service enabled and at least two staff user accounts created.
  2. The AP registered on the RADIUS server as a network access device (client) with a shared secret.
  3. AP-STAFF reconfigured to WPA2-Enterprise, pointing at the RADIUS server's IP with the matching shared secret.
  4. The staff client uses per-user credentials (username + password) rather than a shared key.
  5. Staff client authenticates via RADIUS and associates successfully, obtaining a VLAN 10 IP.
  6. A second AP (AP-GUEST) added on a VLAN 20 access port broadcasting a separate guest SSID.
  7. The guest client associates to the guest SSID and obtains a VLAN 20 IP.
  8. Guest isolation verified — the guest client cannot reach the staff VLAN (Layer 2/3 segmentation).
  9. Staff connectivity preserved — the staff client can still reach internal VLAN 10 resources.
  10. Configuration saved with all settings intact.

Add a guest client

Drag a Smartphone (or laptop with wireless) and rename it GUEST-PHONE. It will join the guest SSID in the Configure tab.

Why a second AP instead of one AP with two SSIDs?

The basic access point in Packet Tracer broadcasts a single SSID. Real enterprise APs broadcast many SSIDs at once and map each to a different VLAN over a trunk — but to keep this lab clean in the simulator, we use a dedicated AP per network (AP-STAFF on VLAN 10, AP-GUEST on VLAN 20). The concept the exam tests — separate SSID + separate VLAN for guests — is identical either way.

With the server and guest AP in place, move to the Configure tab.

Simulator note — captive portals & WPA3

Packet Tracer does not render an actual captive portal web page, and the basic AP does not expose a WPA3 option. Both are exam knowledge covered in the Brief tab. In production, the guest SSID would typically be open (no PSK) with a captive portal intercepting the first HTTP request to force acceptance of terms; and on modern hardware you would choose WPA3 over WPA2 where all clients support it. The hands-on portion here proves the WPA2-Enterprise + RADIUS workflow and guest VLAN isolation, which Packet Tracer does simulate fully.

What "good" looks like
Enterprise auth has more failure points than PSK — diagnose in order

With PSK, only the passphrase can be wrong. With Enterprise, the chain is longer: client credentials → AP-to-RADIUS reachability → shared secret match → user exists in the database → password correct. If a staff client won't connect, walk the chain: can the AP reach 192.168.10.250? Does the AP's secret match the server's? Is the username in User Setup? Is the password right? Checking in that order isolates the break quickly.

When enterprise auth fails.

Seven failure modes. Most enterprise problems are a mismatch between the AP and the RADIUS server.

Staff client never authenticates, even with correct username/password
Cause
The shared secret on the AP doesn't match the secret configured for that AP on the RADIUS server, so the server silently rejects the AP's requests.
Diagnose
Compare the secret in AP-STAFF → Port 1 to the secret in RADIUS → AAA → Network Configuration for AP-STAFF.
Fix
Set both to the identical secret (RADIUSkey1).
All staff clients are rejected; the AAA page looks empty
Cause
The AAA service is switched Off, or no users have been created in User Setup.
Diagnose
RADIUS → Services → AAA — is Service = On? Are there entries under User Setup?
Fix
Turn the AAA service On and add the staff user accounts.
One user can't log in but others can
Cause
That specific username is missing from the RADIUS database, or its password is mistyped on the server or client.
Diagnose
Check User Setup for the exact username and password; compare to what the client is sending.
Fix
Add or correct that user's entry. (This is the strength of Enterprise: one user's problem doesn't affect anyone else.)
The AP can't reach the RADIUS server at all
Cause
A Layer 2/3 path problem — the server's switch port is in the wrong VLAN, the server has the wrong IP/gateway, or routing between them is broken.
Diagnose
From a host in the AP's VLAN, ping 192.168.10.250. If it fails, the AP can't reach RADIUS either.
Fix
Put the server's port in VLAN 10, fix its static IP/gateway, and confirm reachability.
Guest can reach the staff VLAN (isolation failed)
Cause
The guest AP's switch port is in the wrong VLAN (e.g., VLAN 10 instead of 20), or inter-VLAN routing permits guest-to-staff traffic.
Diagnose
Confirm AP-GUEST's port is in VLAN 20 and that the guest client gets a 192.168.20.x address, not a 10.x one.
Fix
Place the guest AP port in VLAN 20. If isolation must be strict, add an ACL blocking guest-to-staff traffic at the Layer 3 device.
Guest client expects a login page but never sees one
Cause
Expectation mismatch — Packet Tracer doesn't render captive portals. The guest network here uses a PSK instead.
Diagnose
Confirm the guest is joining via the PSK (GuestWiFi24), not waiting for a web portal.
Fix
No fix needed in the simulator. Note in your write-up how a captive portal would work in production (intercept first HTTP request → terms/login page → grant access).
A device can't connect to a WPA3-only network
Cause
The client hardware/driver doesn't support WPA3. WPA3 requires both AP and client to support it.
Diagnose
Check whether the client supports WPA3. Older devices only do WPA2.
Fix
Use a WPA3/WPA2 "transition" (mixed) mode so older clients fall back to WPA2 while capable clients use WPA3. (Conceptual — basic Packet Tracer APs are WPA2.)
