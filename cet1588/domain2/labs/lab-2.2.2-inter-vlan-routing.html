Cross the lines with a Layer 3 switch.

Lab 2.2.1 carved one flat network into four isolated VLANs — that solved the security problem but created a new one: Staff can no longer reach Voice, and nobody can reach the internet. VLANs need a router to talk to each other. In this lab you'll add SW-CORE, a Layer 3 multilayer switch, and give each VLAN a Switched Virtual Interface (SVI) on it. Each SVI becomes the default gateway for one VLAN. Inter-VLAN traffic enters the L3 switch on one VLAN's SVI, gets routed at wire speed, and exits on another. You'll also see the legacy alternative — router-on-a-stick (RoaS) — explained side-by-side so you understand both methods on the exam.

From isolated islands to a routed network.

At the end of Lab 2.2.1 you had VLAN isolation working: Staff on VLAN 10 couldn't talk to Guest on VLAN 20, which is exactly what we wanted from a security perspective. But the IT director needs controlled cross-VLAN access — Staff PCs need to reach the Voice gateway for unified communications, both Staff and Guest need internet access, and the network admin needs to reach every VLAN from the Management VLAN.

The solution is to add a Layer 3 device between the VLANs. We'll use a multilayer switch — a device that combines a switch's port density and speed with a router's ability to make Layer 3 forwarding decisions. The L3 switch participates in every VLAN by hosting a Switched Virtual Interface (SVI) per VLAN. Each SVI has an IP address that becomes the default gateway for the hosts in that VLAN.

Network+ Context — Read this first

The Network+ N10-009 exam is vendor-neutral. You will not be asked to type Cisco commands on test day. So why are we using Packet Tracer with Cisco IOS? Because the most effective way to internalize what a switching concept does is to watch it work in a real environment — and Packet Tracer is the free, industry-standard simulator available to every networking student. The CLI commands in this lab are Cisco's implementation of vendor-neutral concepts the exam tests. Focus on what each command accomplishes, not on memorizing its syntax. Each configuration block below is labeled with the underlying Network+ concept it demonstrates.

METHOD 1

SVI on a Layer 3 Switch

How it works
Multilayer switch creates a virtual Layer 3 interface (SVI) for each VLAN. Each SVI has an IP and acts as the default gateway for that VLAN.
Performance
Wire-speed (ASIC-based forwarding)
Pros
Fast, scales to many VLANs, single device manages both switching and routing
Cons
Requires a multilayer (more expensive) switch
When to use
Enterprise networks, anywhere performance matters
Compared in callouts
METHOD 2 (legacy)

Router-on-a-Stick (RoaS)

How it works
A separate router connects to the switch via one trunk. The router creates a subinterface per VLAN; each subinterface has an IP that acts as the gateway.
Performance
CPU-based forwarding — slower; whole trunk shares one physical link
Pros
Cheap — reuses any router you already have
Cons
Single link becomes a bottleneck; doesn't scale
When to use
Small offices, lab environments, or where a multilayer switch isn't available

Why this matters for the Network+ exam

Objective 2.2 explicitly names inter-VLAN routing. Expect exam questions about how VLANs reach each other, what a Layer 3 switch does, what an SVI is, and the comparison between SVI and router-on-a-stick. The exam loves the trick question: "PC-A in VLAN 10 cannot ping PC-B in VLAN 20 — what is the cause?" The answer is usually missing inter-VLAN routing or a missing default gateway on the host.

Add SW-CORE

Drag a 3560 multilayer switch onto the canvas

From the device tray: Switches → drag 3560-24PS (or similar 3560 variant). Place it above and between SW-FLOOR1 and SW-FLOOR2. Rename it SW-CORE via Config → Display Name. The 3560 is multilayer — it has Layer 3 routing capability that the 2960 access switches lack.

Connect SW-CORE to both access switches with trunk links

Use Copper Crossover for switch-to-switch:

  • SW-CORE Gi0/1 ↔ SW-FLOOR1 Gi0/2 (use a free Gigabit port)
  • SW-CORE Gi0/2 ↔ SW-FLOOR2 Gi0/2

The original SW-FLOOR1 ↔ SW-FLOOR2 trunk from Lab 2.2.1 can remain in place — it provides redundancy. STP (covered in Lab 2.2.3) will prevent the loop.

Update PC default gateways

Add the default gateway to every PC

Click each PC → Desktop → IP Configuration. Add the appropriate gateway from the IP plan:

  • PC-S1, PC-S2 (VLAN 10) → gateway 192.168.10.1
  • PC-G1, PC-G2 (VLAN 20) → gateway 192.168.20.1

Without these gateways, the PCs have no way to send traffic destined for another VLAN — they'll send it to "0.0.0.0" and the switch will drop it.

The "I forgot the gateway" trap

This is the #1 failure mode on this lab. A PC with no default gateway can still ping anything in its own VLAN, but anything cross-VLAN fails silently with "destination unreachable." The PC thinks the destination is on the same network and doesn't know to forward to a router. Always check ipconfig on the PC if a cross-VLAN ping fails.

Once SW-CORE is wired up and PC gateways are set, move to the Configure tab.

Bring up the L3 boundary.

Three configuration blocks. SW-CORE gets the most work — VLAN database, trunks, SVIs, and the critical global command that enables routing. SW-FLOOR1 and SW-FLOOR2 only need one small change each: a default gateway so they can be managed from outside VLAN 99.

Alternative method: Router-on-a-Stick

If you didn't have a multilayer switch, you'd accomplish the same thing with a regular router and a single trunk connection to the switch. The router would have one physical interface (say Gi0/0) and three subinterfaces (Gi0/0.10, Gi0/0.20, Gi0/0.30), each tagged with its VLAN ID using the encapsulation dot1Q command. The subinterface IPs would serve the same role as our SVIs. This is called "router-on-a-stick" (RoaS) because all VLANs share the single physical link. It works but is slower (CPU-based routing) and doesn't scale beyond a few VLANs. You don't need to configure RoaS in this lab — but the Network+ exam expects you to recognize it and know the trade-offs.

The hidden command: ip routing

On a multilayer switch, simply creating SVIs is not enough — the global ip routing command must be enabled for the switch to actually forward traffic between VLANs. Without it, the SVIs come up, the PCs have valid gateway IPs, but cross-VLAN pings still fail silently. If your lab "should work" but doesn't, check this first.

When inter-VLAN won't route.

Seven failure modes. The first three account for ~80% of student lab failures on this exercise.

Cross-VLAN ping fails silently — no error, just timeouts
Cause #1
The PC has no default gateway configured. Without a gateway, the PC has no way to send traffic outside its own subnet.
Cause #2
SW-CORE doesn't have ip routing enabled globally. SVIs are up but the switch refuses to route between them.
Diagnose
On the PC: ipconfig — check Default Gateway. On SW-CORE: show ip route — if it says "IP routing is not enabled", that's your problem.
Fix
PC: add the correct gateway. SW-CORE: in global config, ip routing.
PC-S1 can ping its own gateway 192.168.10.1, but cannot ping PC-G1 in VLAN 20
Cause
Routing is half-working. SW-CORE can receive from VLAN 10 but can't deliver to VLAN 20 — usually the VLAN 20 SVI is missing, shut, or has the wrong IP.
Diagnose
On SW-CORE: show ip interface brief | include Vlan. All four SVIs should be up/up.
Fix
Re-create the missing/wrong SVI. interface Vlan20 / ip address 192.168.20.1 255.255.255.0 / no shutdown.
SVI shows up/down or down/down on SW-CORE
Cause
An SVI only becomes "up/up" when at least one access port in that VLAN is also up. If VLAN 30 has no active access ports anywhere in the network (because the IP phone is unplugged or VLAN 30 isn't allowed on any trunk reaching an active port), the SVI stays down.
Diagnose
show vlan brief on each switch — confirm VLAN 30 exists everywhere. show interfaces trunk — confirm 30 is in the allowed list on every trunk. Confirm the phone is powered on.
Fix
Ensure the VLAN exists locally on SW-CORE (in the VLAN database) and at least one trunk carries it to a switch where a port is active in that VLAN.
Cross-VLAN ping intermittent — sometimes works, sometimes fails
Cause
Two L3 gateways for the same VLAN. If SW-CORE has VLAN 20 SVI at 192.168.20.1 and someone accidentally configured an SVI for VLAN 20 on SW-FLOOR1 at 192.168.20.2, hosts may have inconsistent ARP entries.
Diagnose
On every switch: show ip interface brief | include Vlan. Only SW-CORE should have user-VLAN SVIs (10, 20, 30). Access switches should only have Vlan99.
Fix
Remove the rogue SVI: no interface Vlan20 on the access switch.
Same-VLAN ping (PC-S1 to PC-S2) suddenly stops working after adding SW-CORE
Cause
Likely an STP loop or block. The new SW-CORE trunks plus the existing inter-floor trunk create a Layer 2 loop, and STP has put one of the trunk ports in blocking state — possibly the wrong one.
Diagnose
On each switch: show spanning-tree. Look for any port in BLK (blocking) state.
Fix
Lab 2.2.3 covers STP tuning. For now, you can either shut down the original SW-FLOOR1↔SW-FLOOR2 trunk (no longer needed once SW-CORE is in place) or accept that STP is working as designed.
The SW-FLOOR1 switch can ping SW-CORE but not anything in VLAN 10
Cause
SW-FLOOR1 has no ip default-gateway set. As a Layer 2 device, its management traffic needs a static default route to reach anything outside VLAN 99.
Diagnose
On SW-FLOOR1: show running-config | include default-gateway. If empty, that's the issue.
Fix
ip default-gateway 192.168.99.254 (SW-CORE's VLAN 99 SVI).
First ping after enabling routing always times out, then works
Cause
ARP resolution. Same as in previous labs — the first packet that needs ARP is silently dropped while the reply is being received. Totally normal.
Diagnose
Re-run the ping. Subsequent pings succeed.
Fix
No fix needed. Document this in your lab report so your instructor knows you understand it.
