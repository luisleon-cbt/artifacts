Stop the storm with Spanning Tree.

Three switches connected in a triangle creates a physical loop — and a loop at Layer 2 is catastrophic. With no TTL field in an Ethernet frame, a single broadcast circles forever, multiplying at each switch until the network melts down in seconds. Spanning Tree Protocol (STP) is the safeguard: switches exchange BPDUs, elect a single root bridge, and deliberately block one redundant path so the active topology is loop-free — while keeping that blocked path on standby for instant failover. In this lab you'll force SW-CORE to become the root bridge, observe the port roles STP assigns, enable PortFast on access ports, then break the active path and watch the blocked link take over.

The loop you built on purpose.

Look at the topology you've built across the last two labs. SW-CORE connects to SW-FLOOR1 and to SW-FLOOR2. And from Lab 2.2.1, SW-FLOOR1 still connects directly to SW-FLOOR2. Three switches, three links, arranged in a triangle. That triangle is a Layer 2 loop — and without Spanning Tree, it would destroy the network.

Here's why: when a switch receives a broadcast frame (like an ARP request), it floods it out every port except the one it arrived on. In a triangle, that broadcast travels SW-CORE → SW-FLOOR1 → SW-FLOOR2 → back to SW-CORE → and around again, forever. Ethernet frames have no TTL to kill looping packets the way IP packets have at Layer 3. Within seconds the loop saturates every link — a broadcast storm — and the network is unusable. STP exists to make redundant physical links safe by ensuring only a loop-free subset is active at any one time.

How STP decides — root bridge election

STP's first job is to elect a single root bridge — the reference point for the entire tree. Every switch advertises its Bridge ID (BID), which is priority + MAC address. The switch with the lowest BID wins. Since all switches default to priority 32768, the election would otherwise come down to the lowest MAC address — unpredictable. So network engineers manually set a low priority on the switch they want to be root (usually the core/distribution switch, because all traffic flows through it). We'll set SW-CORE to priority 4096, guaranteeing it wins.

Port roles STP assigns
Root Port (R)
One per non-root switch · forwarding

The single port on each non-root switch that has the best (lowest-cost) path back to the root bridge. Always forwarding. Every non-root switch has exactly one.

Designated Port (D)
One per segment · forwarding

The forwarding port responsible for a given segment's traffic toward the root. Every port on the root bridge is designated. Always forwarding.

Blocking Port (B)
Loop prevention · not forwarding

A port that would create a loop if it forwarded. STP puts it in blocking state — it still listens to BPDUs but drops data frames. If the active path fails, it transitions to forwarding to restore connectivity.

Take control of the tree.

Three configuration blocks. SW-CORE is forced to become root via a low priority and switched to RSTP. The two access switches also get RSTP plus PortFast and BPDU Guard on their end-host ports.

Configuration · 01 of 03 — make it root Concept: RSTP · root bridge election via lowest priority (Bridge ID) SW-CORE 
! ===== SW-CORE — Force this switch to be the STP root bridge =====
enable
configure terminal

! ----- Switch to Rapid STP (RSTP) — faster convergence -----
! 'rapid-pvst' runs one RSTP instance per VLAN.
spanning-tree mode rapid-pvst

! ----- Force SW-CORE to be root for all our VLANs -----
! Lowest priority wins the root election. Default is 32768.
! Priority must be a multiple of 4096. We use 4096.
spanning-tree vlan 10,20,30,99 priority 4096

! ----- Alternative one-liner Cisco provides (does the math for you):
!   spanning-tree vlan 10,20,30,99 root primary
! It sets the priority low enough to guarantee root. Either approach is fine. -----

end

The cardinal rule of PortFast

Never enable PortFast on a switch-to-switch link or a trunk. PortFast tells STP "this port connects to an end device, so skip the loop-prevention wait." If you apply it to a link that actually connects to another switch, you create a window where a loop can form before STP detects it — exactly the disaster STP exists to prevent. PortFast is for access ports facing PCs, printers, and phones only.

Why force the root bridge manually?

If you let STP elect a root automatically, the winner is decided by the lowest MAC address — essentially random, and often an access switch instead of the core. That leads to suboptimal traffic paths (data zig-zagging through an access switch to reach the core). By manually setting SW-CORE to priority 4096, you guarantee the most central, highest-capacity switch is the root, so the active tree matches the physical hierarchy.

The Altn / BLK port is the heart of this lab. STP chose to block this single port — keeping the link physically up but logically idle — so the triangle has no loop. If the root port (Gi0/2) ever fails, this alternate port becomes the new root port almost instantly under RSTP.

When the tree misbehaves.

Seven STP failure modes. The first — a broadcast storm — is the catastrophe STP exists to prevent, and what you'd see if STP were ever disabled.

Network grinds to a halt; link lights blink rapidly in unison; switch CPU at 100%
Cause
A broadcast storm — a Layer 2 loop with no STP blocking it. Frames circle the triangle endlessly, multiplying. This is the disaster STP prevents.
Diagnose
show spanning-tree summary — if STP is disabled or a port that should block is forwarding, you have a loop. show interfaces | include rate shows traffic pinned at line rate.
Fix
Re-enable STP (spanning-tree mode rapid-pvst). If a switch had STP disabled, that was almost certainly the cause. As an emergency stopgap, physically disconnect one leg of the loop.
An access switch became root instead of SW-CORE
Cause
You didn't lower SW-CORE's priority, so the election fell back to lowest MAC address — and an access switch happened to win.
Diagnose
show spanning-tree vlan 10 on SW-CORE — if it does NOT say "This bridge is the root", the priority wasn't applied.
Fix
On SW-CORE: spanning-tree vlan 10,20,30,99 priority 4096 (or root primary). Re-verify.
A PC takes ~30 seconds to get network access after plugging in
Cause
PortFast is not enabled on that access port. The port is cycling through STP listening and learning states before forwarding.
Diagnose
show spanning-tree interface Fa0/1 portfast — if "disabled", that's the delay source.
Fix
On the access interface: spanning-tree portfast. The PC will now get a link almost immediately.
A port unexpectedly went into err-disabled state
Cause
BPDU Guard triggered. A BPDU arrived on a PortFast port, meaning someone connected a switch (or a BPDU-sending device) where only an end host was expected.
Diagnose
show interfaces status err-disabled lists the port and reason (bpduguard).
Fix
Remove the unauthorized device, then re-enable the port: shutdown then no shutdown. (This is BPDU Guard working as designed — it protected your topology.)
After a link failure, recovery takes 30-50 seconds instead of being near-instant
Cause
The switches are running classic STP (802.1D), not RSTP (802.1w). Classic STP's listening + learning timers are slow.
Diagnose
show spanning-tree summary — check the mode. If it says "ieee"/"pvst" instead of "rstp"/"rapid-pvst", it's the slow version.
Fix
On all switches: spanning-tree mode rapid-pvst. RSTP converges in about a second.
Two ports are blocking instead of one
Cause
In a simple triangle, only one port should block. Extra blocking can indicate a duplex or path-cost mismatch making STP see phantom paths.
Diagnose
show spanning-tree blockedports. In a 3-switch triangle, expect exactly one blocked port.
Fix
Check that all trunk links are full-duplex with consistent path costs. Mismatched speeds change STP cost calculations.
Failover doesn't happen — when the active link fails, connectivity is lost permanently
Cause
The "redundant" link isn't actually a working trunk — it may be misconfigured (wrong allowed VLANs or mismatched native VLAN) so STP can't use it as a backup.
Diagnose
show interfaces trunk on both ends of the backup link — confirm it's trunking and carries the same VLANs as the primary path.
Fix
Correct the trunk config on the backup link so it matches: same native VLAN, same allowed-VLAN list.
