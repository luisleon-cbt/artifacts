Two protocols, one network — redistribution.

Real networks rarely run one protocol everywhere. After a merger, an upgrade, or a split between business units, you'll find EIGRP on one side and OSPF on the other. They don't talk to each other natively — they're different protocols. The router that sits between them must be configured to translate routes from one into the other: route redistribution. In this lab you'll run EIGRP between Miami and Atlanta, OSPF between Atlanta and Houston, and use R-ATLANTA as the Autonomous System Boundary Router (ASBR) redistributing both ways.

The merger.

CBT Networks just acquired the Houston branch from another company. The Houston side has historically run OSPF. The Miami and Atlanta sides have always run EIGRP. Your manager wants the networks integrated, but doesn't want to renumber or re-configure either side's internal routing — both teams have been running their protocols for years and don't want disruption.

Network+ Context — Read this first

The Network+ N10-009 exam is vendor-neutral. You will not be asked to type Cisco commands on test day. So why are we using Packet Tracer with Cisco IOS? Because the most effective way to internalize what a routing concept does is to watch it work in a real environment — and Packet Tracer is the free, industry-standard simulator available to every networking student. The CLI commands in this lab are Cisco's implementation of vendor-neutral concepts the exam tests. Focus on what each command accomplishes, not on memorizing its syntax. Each configuration block below is labeled with the underlying Network+ concept it demonstrates.

The solution: leave EIGRP on the west side, leave OSPF on the east side, and configure R-ATLANTA — which sits at the boundary — to participate in both protocols and translate routes between them. This is exactly what real network engineers do during mergers, datacenter consolidations, and ISP-to-ISP edges.

What R-ATLANTA must do
  • Run EIGRP AS 100 on its serial interface toward Miami (S0/0/0) and on its LAN (G0/1).
  • Run OSPF process 1 area 0 on its serial interface toward Houston (S0/0/1) and on its LAN (G0/1) — same LAN appears in both protocols.
  • Redistribute EIGRP into OSPF — take routes learned via EIGRP and re-announce them as OSPF external (E2) routes to R-HOUSTON.
  • Redistribute OSPF into EIGRP — take routes learned via OSPF and re-announce them as EIGRP external (D EX) routes to R-MIAMI.
  • Provide seed metrics — EIGRP needs a starter bandwidth/delay tuple when receiving routes from a non-EIGRP source; OSPF assigns cost 20 by default.

Why this matters for the exam

N10-009 objective 2.1 tests EIGRP, OSPF, administrative distance, and route selection. The redistribution scenario is the cleanest way to see AD in action: the same destination network shows up in both protocols, and the lower AD wins on every router. Confirm baseline OSPF connectivity

Quick ping from PC-M to PC-H. If it succeeds via OSPF, you're in the right starting state. If it fails, fix Lab 2.1.2 first.

Remove OSPF from R-MIAMI

On R-MIAMI, shut down OSPF entirely

R-MIAMI will run EIGRP only. The fastest way to remove OSPF is one global command: no router ospf 1. That removes the process and all its network statements in a single sweep.

Verify connectivity is now broken

From PC-M try to ping PC-A. It will fail — R-MIAMI no longer knows about 10.10.20.0/24. Expected. EIGRP will restore reachability in a moment.

Trim OSPF on R-ATLANTA

Remove the Miami-facing serial from OSPF

R-ATLANTA must keep OSPF running on its Houston-facing serial and its LAN, but the Miami serial belongs to EIGRP now. Under router ospf 1, issue no network 10.0.12.0 0.0.0.3 area 0.

Leave OSPF intact on R-HOUSTON

R-HOUSTON's config doesn't change. It stays an OSPF-only stub — it has no idea EIGRP exists.

Why not just no router ospf 1 on R-ATLANTA too?

Because R-ATLANTA still needs to talk to R-HOUSTON via OSPF. Half its interfaces stay OSPF, half become EIGRP — that's the entire point of an ASBR. Removing the whole OSPF process would also kill the eastward connectivity.

Once OSPF is gone from R-MIAMI and trimmed on R-ATLANTA, move to the Configure tab to bring up EIGRP and set up mutual redistribution.

EIGRP on the west, redistribution on R-ATLANTA.

Three configuration blocks. Apply them in order. R-MIAMI gets EIGRP. R-ATLANTA gets EIGRP plus redistribution commands inside both routing processes. R-HOUSTON stays exactly as it was in Lab 2.1.2 — no changes needed.

EIGRP network statement syntax

Like OSPF, EIGRP uses wildcard masks: network 10.10.10.0 0.0.0.255 matches the /24. You can also use the classful form (network 10.0.0.0) which matches every interface in the 10.0.0.0/8 — easier to type but advertises more than you might intend. We'll use explicit wildcards.

Configuration · 01 of 03 Concept: Hybrid routing protocol · EIGRP AD = 90 · composite metric (bandwidth + delay) R-MIAMI 
! ===== R-MIAMI — Pure EIGRP edge router =====
configure terminal
! Tear down all of OSPF in one command
no router ospf 1

! ----- Bring up EIGRP AS 100 -----
router eigrp 100
 ! Disable auto-summary — we want classless behavior
 no auto-summary
 ! Advertise the Miami LAN
 network 10.10.10.0 0.0.0.255
 ! Advertise the WAN serial subnet
 network 10.0.12.0 0.0.0.3
 ! Silence Hello packets on the LAN — no EIGRP neighbors live there
 passive-interface GigabitEthernet0/1
exit
end
copy running-config startup-config
Configuration · 02 of 03 — the ASBR Concept: Mutual route redistribution · ASBR · external route AD = 170 R-ATLANTA 
! ===== R-ATLANTA — Autonomous System Boundary Router =====
configure terminal

! ----- Trim OSPF to east side only -----
router ospf 1
 ! Remove the Miami-facing serial from OSPF
 no network 10.0.12.0 0.0.0.3 area 0
 ! Keep these — east side and LAN stay in OSPF
 ! network 10.10.20.0 0.0.0.255 area 0  (already there)
 ! network 10.0.23.0  0.0.0.3   area 0  (already there)
 ! ----- Redistribute EIGRP routes INTO OSPF -----
 ! When R-ATLANTA learns 10.10.10.0/24 from EIGRP, advertise
 ! it to R-HOUSTON as an OSPF external (E2) route.
 ! 'subnets' is required, otherwise OSPF only redistributes classful nets
 redistribute eigrp 100 subnets
exit

! ----- Bring up EIGRP AS 100 -----
router eigrp 100

 ! Advertise the Miami-facing serial
 network 10.0.12.0 0.0.0.3
 ! Advertise the Atlanta LAN (same subnet appears in OSPF too)
 network 10.10.20.0 0.0.0.255
 ! ----- Redistribute OSPF routes INTO EIGRP -----
 ! EIGRP needs SEED METRIC: bandwidth(K) delay(10us) reliability load mtu
 ! Reasonable defaults for a T1: 1544 2000 255 1 1500

 passive-interface GigabitEthernet0/1
exit
end

Understanding the EIGRP seed metric

When you redistribute OSPF into EIGRP, EIGRP needs five numbers to build a composite metric: bandwidth (Kbps), delay (tens of µs), reliability (0–255), load (1–255), MTU (bytes). Without these, the redistributed routes have an infinite metric and EIGRP refuses to install them. The values 1544 2000 255 1 1500 emulate a T1 link — appropriate for a serial WAN. On a Gigabit redistribution, use 1000000 100 255 1 1500.

The "subnets" keyword for OSPF redistribution

If you omit subnets in redistribute eigrp 100 subnets, OSPF will only redistribute classful networks — meaning your /24 LAN routes get summarized or dropped. Always include subnets. It's tested directly on the exam.

When redistribution goes wrong.

Redistribution introduces its own failure modes that don't exist in single-protocol labs. Seven common ones below.

PC-M pings PC-A but cannot ping PC-H
Cause
R-ATLANTA is not redistributing OSPF into EIGRP. R-MIAMI never learns about the east side.
Diagnose
On R-MIAMI: show ip route 10.10.30.0. If empty, redistribution OSPF→EIGRP isn't happening.
Fix
Under router eigrp 100 on R-ATLANTA: redistribute ospf 1 metric 1544 2000 255 1 1500.
Routes redistributed into EIGRP show metric 0 or never install
Cause
Missing the seed metric. EIGRP rejects redistributed routes when it can't compute a composite metric.
Diagnose
On R-ATLANTA: show ip eigrp topology | include EX. If no external routes appear, the seed is the issue.
Fix
Add the five metric values: redistribute ospf 1 metric 1544 2000 255 1 1500. Don't try to use just redistribute ospf 1 — it will accept the command but silently drop the routes.
PC-H pings PC-A but not PC-M (one-way only)
Cause
Redistribution EIGRP→OSPF is missing the subnets keyword. OSPF drops classless routes by default.
Diagnose
On R-HOUSTON: show ip route 10.10.10.0. If empty, OSPF redistribution isn't carrying the /24 across.
Fix
Under router ospf 1 on R-ATLANTA: redistribute eigrp 100 subnets.
EIGRP neighbors won't form between R-MIAMI and R-ATLANTA
Cause
Mismatched AS numbers. EIGRP only forms adjacencies between routers in the same autonomous system.
Diagnose
show ip protocols | include eigrp on both routers. The number after "eigrp" must match (we used 100).
Fix
Remove the wrong process: no router eigrp 200 (or whatever the wrong AS is), then router eigrp 100 with the correct network statements.
R-ATLANTA shows two equal routes for 10.10.20.0/24 — one EIGRP, one OSPF
Cause
The Atlanta LAN is advertised by both protocols on R-ATLANTA. Not a bug — but the routing table will pick the lower AD.
Diagnose
show ip route 10.10.20.0 — only the EIGRP version should appear (AD 90 wins over AD 110).
Fix
No fix required — this is correct behavior. If you want OSPF to win for some operational reason, you'd use distance ospf intra-area 89 to override AD. Not on the exam at the Network+ level.
After saving, R-MIAMI still shows OSPF neighbors on reload
Cause
You forgot no router ospf 1, or you only removed individual network statements without removing the process.
Diagnose
show running-config | section router ospf on R-MIAMI. Should return nothing.
Fix
configure terminal → no router ospf 1 → end → copy run start.
Default route not appearing on R-HOUSTON
Cause
The chain is: R-MIAMI static default → redistributed into EIGRP → propagated to R-ATLANTA → R-ATLANTA must then originate it into OSPF.
Diagnose
On R-ATLANTA: show ip route 0.0.0.0. If you see it as D*EX, EIGRP carried it but OSPF didn't pick it up.
Fix
Under router ospf 1 on R-ATLANTA: default-information originate always. The always keyword tells OSPF to advertise the default whether or not it's locally configured.
