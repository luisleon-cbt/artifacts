The service that translates names.

When a user types www.miami.cbt, their device first has to find the IP address that lives behind that name. DNS (Domain Name System) is the directory that maps names to addresses (and vice-versa). The directory is made of records, each with a specific job: A records hold IPv4 addresses, AAAA records hold IPv6 addresses, CNAME records create aliases, MX records direct mail, PTR records do the reverse , IP back to name. You'll build one of each.

Network+ Context — Read this first

Network+ N10-009 expects you to identify and use the major DNS record types: A (host \u2192 IPv4), AAAA (host \u2192 IPv6), CNAME (alias \u2192 another name), MX (mail server for a domain), PTR (IP \u2192 host, reverse), and a couple more (NS, TXT, SOA). You also need to know forward resolution (name to IP) vs reverse resolution (IP to name), what an authoritative server is, and what a client does when it gets a name. This lab makes all of that concrete.

Forward vs reverse , the key distinction

Forward resolution (the common case): client has a name, asks DNS for the IP. Uses A/AAAA records in a forward zone. Reverse resolution: client has an IP, asks DNS for the name. Uses PTR records in a reverse zone. They use different records and different zones , a server can do forward without doing reverse, which is why reverse lookups so often fail in the real world.

Why this lab matters

Almost every "the Internet is broken" incident is, at some level, a DNS incident , wrong record, expired record, server unreachable, slow lookup. Building a DNS server end-to-end , records, zones, options, verification , is the difference between memorizing what each record type does and actually trusting your name resolution.

Reach the server first

Before you configure records, the clients must be able to reach the DNS server (192.168.99.20). From any client with a DHCP lease: ping 192.168.99.20 must succeed. If it doesn't, fix routing/relay/scope first , a server you can't reach can't answer queries.

Add the DNS server

Drag a Server onto VLAN 99. Set it to Static IP 192.168.99.20, mask 255.255.255.0, gateway 192.168.99.1. Cable it to a VLAN 99 access port.

Add the web/mail server

Drag another Server onto VLAN 99 (call it WEB). Static IP 192.168.99.50. Under Services, leave HTTP On so we have something to actually load by name later. For the lab\u2019s purposes this single host plays the roles of web, server, and mail.

Update the DHCP DNS option

On the DHCP server (Lab 3.4.1), make sure each scope\u2019s DNS Server option is set to 192.168.99.20 (the DNS server, not the DHCP server). If the scopes still point at the wrong address from earlier work, fix them now so leased clients learn the DNS server automatically.

Build the records, one type at a time.

All record work happens in Packet Tracer\u2019s Services \u2192 DNS on the DNS server. The pattern is the same for every record: pick a type, fill in Name and Address (or Target/Host for the non-address types), click Add, and verify in the list below the form.

The mechanics in one sentence

Packet Tracer\u2019s DNS server isn\u2019t enterprise-grade, but it implements the parts the exam cares about: type-specific records (A/AAAA/CNAME/MX/NS/SOA), reverse PTR entries, and the ability for clients to query by name. Focus on what each record does, not the vendor menus.

One name, two answers , totally normal

A host can have both an A and a AAAA record. A client that asks for the IPv4 address gets the A; one that asks for IPv6 gets the AAAA. This is how dual-stack networks work in practice.

Packet Tracer scope note , the zone behind the curtain

On real DNS servers, reverse lookups use a special zone tied to the address range , for 192.168.99.0/24 it\u2019s 99.168.192.in-addr.arpa. Packet Tracer hides that machinery; just adding the PTR with the IP as the “name” is enough. The exam may ask about the .in-addr.arpa naming, so it\u2019s worth knowing even though PT doesn\u2019t show it.

Part G · Renew clients so they pick up the DNS server

If the DHCP option still pointed at the wrong server, the clients are holding stale info. From each test client\u2019s Desktop \u2192 IP Configuration, toggle Static then back to DHCP (or click Renew). The new lease arrives with DNS Server = 192.168.99.20.

When names don\u2019t resolve.

Almost every DNS failure is one of a small set of root causes. The symptom is usually generic (“the website won\u2019t load”), but the diagnosis is mechanical: where in the chain did the lookup fail?

Client gets "DNS request timed out" or "server failed to respond"
Symptom
nslookup hangs and times out; ping-by-name fails.
Likely cause
Client can\u2019t reach the DNS server , wrong DNS address pushed by DHCP, server down, or no route.
Diagnose
ipconfig /all on the client (correct DNS server?). From the client: ping 192.168.99.20 (reachable?).
Fix
Correct the DHCP scope\u2019s DNS option and renew, or restore reachability to the server.
"Server can\u2019t find name" / NXDOMAIN
Symptom
DNS responds, but says the name doesn\u2019t exist.
Likely cause
The record is missing or misspelled on the DNS server (or the user typed the wrong name).
Diagnose
Open the server\u2019s DNS record list and search for the exact name. Check for typos (wwwmiami.cbt vs www.miami.cbt).
Fix
Add or correct the record; nslookup should resolve on the next query.
CNAME resolves to a name but no address
Symptom
nslookup on the alias returns the canonical name but no IP, or the chain breaks.
Likely cause
The CNAME\u2019s target has no A (or AAAA) record. A CNAME points to a name; that name must itself resolve.
Diagnose
nslookup the target name directly. If it fails, the A record is missing.
Fix
Add the A/AAAA record for the CNAME\u2019s target.
Forward works, reverse fails
Symptom
nslookup name succeeds; nslookup IP returns "non-existent domain."
Likely cause
No PTR record for that IP , forward and reverse are separate. Adding an A doesn\u2019t auto-create a PTR.
Diagnose
Check the DNS server\u2019s PTR records for the target IP.
Fix
Add the PTR. The reverse zone (x.x.x.in-addr.arpa) and the forward zone are managed independently , a very common real-world miss.
Packet Tracer scope note

Packet Tracer simulates the parts the exam tests , zone-less record management, A/AAAA/CNAME/MX/PTR, NS/SOA, and basic forwarding. It does not implement DNSSEC, DoH/DoT (covered in Explorer 3.4.4), advanced split-horizon, or real recursive/iterative behavior. Your nslookup output is also simpler than a real Windows nslookup. The concepts you exercised here , record types, forward vs reverse, the option to push DNS via DHCP , are the exam-tested ones.
