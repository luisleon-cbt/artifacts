From "what" to "watch it happen."

In the explorers you learned that syslog pushes event messages to a central server and SNMP lets a manager poll devices for health. This lab makes both concrete on the familiar Miami network: three switches will send their logs to a syslog server, and a management PC will be able to poll them via SNMP. Then you'll trigger an event and watch the log arrive , proving the push model with your own eyes.

Network+ Context — Read this first

The Network+ N10-009 exam is vendor-neutral , you won't type these exact commands on test day. But configuring syslog and SNMP once makes the concepts stick: you'll see that syslog is push (the switch sends a message the instant the interface changes) and that SNMP is largely pull (the manager requests values using a community string). Packet Tracer simulates both well. Focus on the roles , logging host, severity, SNMP community/polling , not the syntax.

What you'll build
  • A central Syslog Server on the management subnet, receiving event messages from all three switches.
  • Each switch (SW-CORE, SW-FLOOR1, SW-FLOOR2) configured with a logging host pointing at that server.
  • An SNMP community string on each switch so the Management PC can poll them (read-only).
  • A deliberate interface flap (shut/no-shut) to generate a live syslog message you can watch land on the server.

Why this lab matters

A network you can't observe is a network you can't operate. Centralizing logs (syslog) and enabling polling (SNMP) are the first two things real teams turn on after a device is in production , they're how you find out something broke before a user calls. You'll do exactly that here, then watch it work.

Reachability first

Syslog and SNMP only work if the switches can reach the management subnet. Before configuring either, confirm each switch can ping 192.168.99.10 (the syslog server). If a switch can't reach it, fix management IP / gateway / VLAN 99 first , monitoring can't traverse a path that doesn't exist.

Place the two management devices

Add the Syslog Server

Drag a Server from End Devices onto the management area. Set Config → FastEthernet0 → IP 192.168.99.10, gateway 192.168.99.1. Cable it to a VLAN 99 access port (on SW-CORE for simplicity). Under Services → SYSLOG, make sure the service is On.

Add the Management PC

Drag a PC onto the management area. Set IP 192.168.99.11, gateway 192.168.99.1, on a VLAN 99 port. This PC's Desktop → MIB Browser is your SNMP manager.

Verify management reachability

From each switch CLI, ping 192.168.99.10 and ping 192.168.99.11. All should succeed before you continue. This is the path your monitoring traffic will use.

Turn on syslog and SNMP.

Two short jobs per switch: point logging at the syslog server, then enable an SNMP read-only community. The commands below are shown on SW-CORE; repeat the same on SW-FLOOR1 and SW-FLOOR2 (their management IPs differ, but the syslog host and SNMP community are identical).

What each command is doing

Don't memorize syntax for the exam , understand the roles. The logging host tells the switch where to push syslog messages. The logging trap level sets which severities to send (0\u2013N). The snmp-server community creates the shared string a manager must present to poll, and RO makes it read-only.

Part A · Syslog (on each switch)
CLI · IOS Concept: a "logging host" is where the switch pushes its event messages SW-CORE 
SW-CORE> enable
SW-CORE# configure terminal
! send logs to the central syslog server
SW-CORE(config)# logging host 192.168.99.10
! send severity 0 through 6 (informational and worse)
SW-CORE(config)# logging trap informational
! timestamp each message so log review is meaningful
SW-CORE(config)# service timestamps log datetime msec
SW-CORE(config)# end
SW-CORE# write memory
Building configuration...
[OK]
About logging trap informational

This sets the threshold to level 6 (Informational) , the switch will push severities 0\u20136 and hold back only level 7 (Debug). That mirrors the threshold slider from Explorer 3.2.2: lower number = more severe, and a threshold of N captures 0\u2013N. Leave it at informational for this lab so you see plenty of messages.

Part B · SNMP read-only community (on each switch)
CLI · IOS Concept: the community string is the "password" a manager presents to poll SW-CORE 
SW-CORE# configure terminal
! read-only community string the manager must match
SW-CORE(config)# snmp-server community CBTmon RO
! optional descriptive info shown to the manager
SW-CORE(config)# snmp-server location Miami-MDF
SW-CORE(config)# snmp-server contact NetOps
SW-CORE(config)# end
SW-CORE# write memory
[OK]

The moment that matters

Checks 7 and 8 are the whole point: you cause an event and a message appears on the server on its own, with no request from you. That's push , the defining behavior of syslog. Contrast it with check 6, where you had to ask the switch for a value: that's pull.

When the logs don't show up.

Monitoring has its own failure modes , and they're quietly dangerous, because a silent monitoring system looks just like a healthy one. Here are the usual suspects when syslog or SNMP isn't working.

No syslog messages arrive at the server at all
Symptom
You flap a port but the server's message table stays empty.
Likely cause
The switch can't reach the server, or no logging host is set, or it points at the wrong IP.
Diagnose
ping 192.168.99.10 from the switch; show run | include logging to confirm the host line.
Fix
Restore VLAN 99 reachability / gateway, then set logging host 192.168.99.10.
Some events log, but not the ones you expect
Symptom
Serious events appear, but routine informational messages never do (or vice-versa).
Likely cause
The logging trap level (threshold) is set too low , it's filtering out the severities you wanted.
Diagnose
Check the trap level; remember a threshold of N sends only severities 0\u2013N.
Fix
Raise the level (e.g., to informational / 6) to include the messages you need.
SNMP poll times out / returns no data
Symptom
The MIB Browser shows a timeout or error when you click Go.
Likely cause
The community string doesn't match (case-sensitive), the wrong device IP, or SNMP isn't configured on that switch.
Diagnose
Compare the manager's read community to show run | include snmp; verify the target IP.
Fix
Make the community identical on both ends (CBTmon) and target a reachable management IP.
Timestamps are missing or meaningless
Symptom
Messages arrive but you can't tell when events happened, making log review useless.
Likely cause
Timestamps aren't enabled (and ideally the device's clock/NTP isn't set).
Diagnose
Look at the time column , uptime counters instead of real dates is the tell.
Fix
Enable service timestamps log datetime; in production, sync time via NTP so all devices agree.
Packet Tracer scope note

Packet Tracer simulates the core behavior , logging host, severity filtering, SNMP community polling, and live link-state messages , faithfully enough to learn the concepts. It does not implement every real-world syslog/SNMP feature (full MIB trees, SNMPv3 auth/encryption, advanced filtering). On real gear and the exam, remember SNMPv3 adds authentication and encryption that v2c communities lack.

Package it for grading.
