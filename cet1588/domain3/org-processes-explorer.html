The complete reference.

Domain 3.1 covers four interrelated topics: documentation (what records you maintain so someone else can understand and operate your network), life-cycle management (when to retire hardware and software), change management (how you make modifications without causing outages), and configuration management (how you track and restore device configurations). Get any of these wrong and you'll spend the rest of your career fighting fires.

Documentation — The Records You Keep
PHYSICAL DIAGRAM

What it looks like

Shows the physical reality: cabinets, racks, cables, switches, server locations, room layout. Used by technicians who need to find or troubleshoot equipment.

USE WHEN: Tracing a bad cable, planning a hardware install, replacing equipment.

LOGICAL DIAGRAM

How traffic flows

Shows the logical structure: VLANs, IP subnets, routing relationships, security zones. Abstracts away physical layout to show how data moves.

USE WHEN: Designing changes, troubleshooting routing, security audits.

LAYER 1 / 2 / 3 DIAGRAMS

Layered network views

Layer 1: cables, ports, patch panels.
Layer 2: switches, VLANs, MAC tables, STP.
Layer 3: routers, IPs, subnets, routes. Separating layers keeps each diagram readable.

RACK DIAGRAM

What's in each rack

Front view of a rack showing U-by-U what equipment is mounted. Helps with capacity planning, equipment installation, and finding a specific device in a noisy data center.

CABLE MAP

Cable inventory

Records which patch panel port connects to which switch port and ultimately to which wall jack. Without it, tracing a cable means walking the building.

USE WHEN: Adding new devices, troubleshooting outages, moves/adds/changes (MAC work).

IPAM

IP Address Management

Tracks every IP allocation: who has what, when it was assigned, which subnet it lives in. Modern IPAM tools (Infoblox, phpIPAM, NetBox) integrate with DHCP and DNS.

USE WHEN: Allocating new IPs, troubleshooting duplicate addresses, audit reports.

ASSET INVENTORY

What you own and when it dies

Database of all hardware/software with serial numbers, warranty dates, licenses, purchase dates, and lifecycle status. Critical for budget planning and audit compliance.

TRACK: Hardware, software licenses, warranty support, location.

SLA

Service-Level Agreement

Contractual commitment between IT and customers (internal or external) about service availability and performance — e.g., "99.9% uptime, 4-hour response time."

METRICS: Uptime %, response time, MTTR, hours of support coverage.

WIRELESS HEAT MAP

Wi-Fi coverage visualization

Color-coded floor plan showing signal strength across the building. Produced by site survey tools (Ekahau, NetSpot). Shows weak spots, overlap zones, interference.

USE WHEN: Planning AP placement, troubleshooting Wi-Fi complaints, validating coverage.

NETWORK DIAGRAM

The big picture

High-level overview of how sites, networks, and major systems interconnect. Often shown to executives. Less detail than Layer 1-3 diagrams but easier to absorb at a glance.

Life-Cycle Management — When Things Die
PhaseWhat it meansWhat to do
Active Vendor sells it. Full feature development and support. Normal patching and operation.
End-of-Sale Vendor stops selling new units. Still supported. Plan replacement procurement before EOS.
End-of-Life (EOL) Vendor stops feature development. Still releases critical security patches. Begin replacement planning. New deployments must use successor product.
End-of-Support (EOS) Vendor stops ALL patches, including security. Hardware fails = total loss. MUST be replaced before this date. Operating EOS gear is a security/compliance violation.
SOFTWARE MANAGEMENT

Patches, OS, firmware

Three types of software updates: patches (security and bug fixes), OS upgrades (major version jumps), firmware (low-level device software). All three follow a test → schedule → deploy → verify cycle.

DECOMMISSIONING

Retiring equipment safely

Removing equipment from service requires: (1) back up configs, (2) document what it did, (3) reassign or wipe data, (4) remove from monitoring/IPAM/asset inventory, (5) physically secure or destroy media before disposal.

SECURITY: Drives must be wiped or destroyed before disposal — old configs and data can include passwords, SSH keys, customer data.

Change Management — Don't Break the Network

Change management exists because the most common cause of network outages isn't hardware failure or attacks — it's human error during planned changes. The change management process forces planning, peer review, scheduling, and verification.

Change typeRisk levelApprovalExamples
Standard LOW Pre-approved (no CAB review) Failed switch replacement (same model), routine patches, new user setup, password reset.
Normal MEDIUM Full CAB review VLAN migration, firewall rule changes, OS upgrades, new deployments.
Emergency HIGH Expedited; post-implementation review Production outage requiring immediate action, security incident response.
RFC

Request For Change

The formal ticket initiating a change. Contains: what is being changed, why, when, impact, rollback plan, and who is responsible.

CAB

Change Advisory Board

Cross-functional group that reviews and approves normal changes. Typically includes network, security, ops, application owners, and a business stakeholder.

ROLLBACK PLAN

How you undo it

Step-by-step recipe to revert the change if it fails. Should be tested in staging, not improvised at 3am during the change window. Required field on every RFC.

MAINTENANCE WINDOW

When changes happen

Pre-scheduled period (typically late nights or weekends) when changes are allowed and users expect possible disruption. Outside the window: emergencies only.

POST-IMPLEMENTATION REVIEW

Did it work?

After every change: verify success, check monitoring, document what happened. For emergency changes, this is where the full review happens (since it was skipped before implementation).

SERVICE REQUEST

Not a change

Routine user-facing tasks (account creation, software install, password reset) — handled through a service request workflow, not change management. Lower overhead, faster turnaround.

Configuration Management — Tracking What's Running
PRODUCTION CONFIG

What's running right now

The live configuration on the device. Should always match what's documented and approved. Drift between production and documentation is the #1 source of "it used to work" mysteries.

BACKUP CONFIG

A copy you can restore

Saved configuration that can be loaded onto replacement hardware or used to restore after a failed change. Best practice: automated nightly backups to a config repository with version history.

BASELINE / GOLDEN CONFIG

The approved starting point

Standardized configuration template applied to all devices of a given type (e.g., all access switches start from one golden config). Ensures consistency across the fleet.

TOOLS: Ansible, Cisco DNAC, Nornir, Git-based config repos.

VERSION CONTROL

What changed and when

Storing configs in Git or a similar system gives you per-line diffs of what changed, who changed it, and the ability to roll back to any previous version. Essential for compliance audits.

Common Exam Traps
  • Physical diagram vs logical diagram. Physical = what it looks like (cables, racks). Logical = how it flows (VLANs, subnets, routes). Don't confuse them.
  • EOL vs EOS — different dates. End-of-Life means feature dev stops; the product still gets security patches. End-of-Support means ALL updates stop — replace by this date or you're running unpatched gear.
  • "Standard" change is NOT the default. Standard means pre-approved repeatable. Most non-trivial changes are "normal" requiring full CAB review.
  • Emergency changes still get reviewed — just AFTER. Skipping the post-implementation review is the same as skipping the CAB review in non-emergency cases.
  • Rollback plan is a required field on RFCs. "We'll figure it out" is not a rollback plan.
  • Golden config = template, not a backup. Golden is your approved starting point; backup is a copy of the live running config.
  • IPAM ≠ DHCP. DHCP hands out addresses dynamically. IPAM tracks all assignments (static and dynamic) for the entire network.
  • Decommissioning includes data destruction. Old configs may contain passwords, SSH keys, customer data — wipe or destroy media before disposal.

What this teaches

  • Categorization matters. The three change types (Standard / Normal / Emergency) drive every later decision. Misclassifying a normal change as standard bypasses CAB review — and frequently causes outages.
  • Documentation is not paperwork — it's insurance. A rollback plan you wrote at 2pm is much more useful than the one you try to write at 3am after the change failed.
  • Maintenance windows exist for a reason. Implementing changes during business hours guarantees that any failure affects users immediately and visibly.
  • Verification is when you find out it worked. "Looks fine to me" is not verification. Check monitoring, test the impacted service, confirm the rollback plan is still ready.
