The complete reference.

Domain 4.1 has four major concept families: the CIA triad (the goals security tries to protect), threats, vulnerabilities, and exploits (the vocabulary of risk), access control models (least privilege, RBAC, Zero Trust), and defense in depth with its authentication methods (MFA, RADIUS, TACACS+, SSO, LDAP, Kerberos, SAML, local) plus network-layer controls (segmentation, NAC, screened subnet, honeypot, separation of duties). Plus risk management, SIEM, encryption, and certificate trust.

CIA Triad — What Security Protects
C

Confidentiality

Only authorized parties can read the data. Achieved via encryption (TLS, full-disk, file-level), access controls, and authentication.

Threats: eavesdropping, data theft, unauthorized disclosure
I

Integrity

Data hasn't been altered by unauthorized parties. Achieved via cryptographic hashes (SHA-256), digital signatures, message authentication codes (HMAC).

Threats: tampering, replay attacks, unauthorized modification
A

Availability

The data and services are usable when needed. Achieved via redundancy, capacity planning, DR/HA, DDoS protection.

Threats: DoS/DDoS, ransomware, hardware failure

The triad is the foundation of all security thinking. Every control either supports C, I, or A — and many support more than one. Encryption supports C and I. Backups support I and A. Authentication supports C and I (by preventing unauthorized actions).

Threats, Vulnerabilities, Exploits — The Vocabulary of Risk
THREAT

What could go wrong

An actor or event that could harm the organization. Internal (employee, contractor) or external (cybercriminal, nation-state, hacktivist, script kiddie).

EXAMPLES: ransomware gang, malicious insider, accidental data deletion.

VULNERABILITY

A weakness that could be exploited

A flaw in software, hardware, configuration, or process. Tracked in the CVE (Common Vulnerabilities and Exposures) database with CVSS scores.

EXAMPLE: unpatched OpenSSL flaw with a known CVE.

EXPLOIT

The technique to use the vulnerability

The actual code or method that takes advantage of a vulnerability. A vulnerability without a known exploit is less dangerous; one with public exploit code is critical.

EXAMPLE: Metasploit module for a CVE.

ZERO-DAY

Vulnerability with no patch yet

A flaw that's being actively exploited before the vendor knows about it (or before a patch exists). Extremely dangerous because no signature-based defense exists yet.

DEFENSE: defense in depth, behavioral detection, rapid patching when patch arrives.

RISK

Threat × Vulnerability × Impact

The likelihood of a threat exploiting a vulnerability, weighted by the potential damage. Risk management = identify, assess, treat (accept, transfer, mitigate, or avoid).

INTERNAL vs EXTERNAL

Where the threat lives

Internal: employees, contractors, vendors with legitimate access. Often the highest-impact because they're already inside.
External: anyone outside the organization. Far more numerous but starts with no access.

Access Control Models
LEAST PRIVILEGE

Give the minimum access needed for the job

A user gets ONLY the permissions required for their role — no more. Reduces blast radius when accounts are compromised. Apply to users, services, and systems.

CONTRAST WITH: "everyone is local admin" — opposite of least privilege.

RBAC

Role-Based Access Control

Permissions are assigned to ROLES, not individual users. Users get a role (or several). Easier to manage at scale: when someone changes jobs, you change their role, not edit every individual permission.

EXAMPLES: AD groups, AWS IAM roles, GCP IAM roles.

ZERO TRUST

Never trust, always verify

The traditional "trusted internal network" model is dead. Zero Trust verifies EVERY request — user, device, location, behavior — even from the LAN. No implicit trust based on network position.

PILLARS: verify explicitly, least-privilege access, assume breach.

SEPARATION OF DUTIES

No one person controls a full process

Critical functions split between multiple people so fraud or accidents require collusion. Classic examples: developer can write code but not deploy; admin can create users but not approve their access.

Defense in Depth — The Layered Approach

Defense in depth is the strategy of stacking multiple independent controls so that bypassing one doesn't compromise the whole. If a single layer fails, the others catch it. A real-world example: an attacker has to defeat your edge firewall AND your IDS AND your network segmentation AND your host firewall AND your endpoint detection AND your authentication AND your authorization — all separately — to reach sensitive data.

NETWORK SEGMENTATION

Divide into security zones

VLANs, subnets, firewalls between zones. Limits lateral movement. Production ≠ Dev. Finance ≠ Marketing. IoT ≠ Corporate. Each zone has its own ACL policy.

SCREENED SUBNET (DMZ)

Buffer zone for public-facing servers

A network segment between the internet and your internal network, holding servers that MUST be internet-reachable (web servers, mail relays). If they\'re compromised, attackers can\'t directly reach internal systems.

OLD NAME: DMZ (demilitarized zone) — still used colloquially.

NAC

Network Access Control

Before a device gets a normal IP on the network, NAC checks it — is the OS patched? AV running? Disk encrypted? Domain-joined? If not, device is denied or sent to a remediation VLAN. Often implemented via 802.1X.

HONEYPOT

Fake target that detects attackers

A decoy system designed to look attractive to attackers but isolated from real assets. Any interaction with it is suspicious — legitimate users have no reason to touch it. Provides early warning of intrusion.

SCALE UP: honeynet = network of multiple honeypots.

SIEM

Security Information & Event Management

A platform that aggregates logs from firewalls, servers, EDR, IDS, etc., then correlates events to detect attacks. Centralized visibility + alerting + investigation workflow. Examples: Splunk, Elastic SIEM, Sentinel.

ENCRYPTION

At rest and in transit

Full-disk encryption (BitLocker, FileVault, LUKS) — protects data if laptop is stolen.
File-level encryption — protects specific files even within the same disk.
In-transit — TLS, IPsec.

Authentication Methods — Who You Are, Centralized

Authentication answers "who is this?" — and modern networks rarely store credentials directly on each device. Centralized authentication uses a single identity store with protocols that ask "is this user valid?" on every login.

Certificates — Self-Signed vs Publicly Trusted
SELF-SIGNED CERTIFICATE

Signed by the device itself

The device generates a key pair and signs its own certificate. Free, instant, but browsers and clients won\'t trust it by default — users see a security warning. Acceptable for internal-only services where you control all clients (and can pre-install the cert).

PUBLICLY TRUSTED CA

Signed by a recognized authority

A Certificate Authority (Let\'s Encrypt, DigiCert, Sectigo) that browsers and OSes trust out of the box validates your domain and signs your cert. Required for any public-facing service so users don\'t see warnings.

INTERNAL CA

Your own CA for internal use

You stand up a CA (Windows ADCS, OpenSSL) and configure your endpoints to trust it. Then you can issue trusted certs for internal services without per-cert vendor cost. Used for 802.1X device certs, internal HTTPS, mutual TLS.

PKI

Public Key Infrastructure

The whole system that issues, distributes, validates, and revokes certificates. Includes the CA, the registration authority, the revocation lists (CRL), OCSP responders, and the trust chain back to a root CA.

Common Exam Traps
  • RADIUS for network access; TACACS+ for device admin. Both authenticate users to network devices but have different specialties. RADIUS combines authentication+authorization into one step; TACACS+ separates them and supports per-command authorization.
  • Kerberos is the default in AD environments. When a Windows user logs into a domain-joined PC, they get a TGT (ticket-granting ticket) and use it to access AD-integrated services without re-entering passwords. Requires time sync.
  • SAML for federation (cross-org SSO). When you log into Salesforce or Workday with your corporate credentials, that\'s typically SAML. Browsers redirect the user to your IdP, IdP returns a signed assertion, the SaaS app trusts it.
  • MFA is two factors from different CATEGORIES. Two passwords are not MFA. Password + SMS code IS MFA (something you know + something you have). Password + fingerprint IS MFA.
  • Zero Trust ≠ "trust nothing." It means "never trust based on network position alone — verify every request explicitly." Users still get access; the access is just continuously verified.
  • Honeypot has NO legitimate users. Any interaction with it is a security event. That\'s the whole point — separates signal from noise.
  • Self-signed certs are not insecure — they just lack public trust. If you control the clients, self-signed is fine. For public services, you need a publicly-trusted CA.
  • Defense in depth ≠ buying more products. It\'s about LAYERED INDEPENDENT controls. Two firewalls from the same vendor isn\'t defense in depth — they\'ll have the same vulnerabilities.
  • CVE = Common Vulnerabilities and Exposures. Each tracked vulnerability gets a CVE ID (CVE-2024-12345). CVSS scores rate severity from 0-10.

What this teaches

  • Different users need different auth + defense combinations. Employees use SSO with RBAC. Admins use TACACS+ and jump boxes. Vendors use time-limited DMZ accounts. IoT uses certificate-based 802.1X. The exam\'s "scenario → architecture" questions reward students who recognize the pattern.
  • Defense in depth is the consistent thread. Every scenario stacks multiple controls — segmentation + authentication + monitoring + audit — so no single failure exposes the asset.
  • Least privilege scales with sensitivity. A read-only employee account is fine for most apps; an admin account needs MFA, separation of duties, and session recording.
  • Zero Trust applies everywhere. "They\'re on the VPN" is not a reason to grant broad access. Continuous verification + network segmentation behind the VPN limits damage when (not if) credentials are stolen.

Authentication methods compared.

The exam tests whether you can pick the right authentication method for a scenario. Each method has a specialty — RADIUS for network access, TACACS+ for device admin, Kerberos inside AD, SAML for SaaS SSO, LDAP as the underlying directory. Memorize the ports, but more importantly memorize the use-case.

MethodPortBest ForKey Properties
MFA N/A Any authentication — layer it on top Two or more factors from different categories: know (password, PIN), have (phone, hardware token, smart card), are (fingerprint, face). 2FA = exactly 2; MFA = 2 or more.
RADIUS UDP 1812 (auth), UDP 1813 (acct) Network access — VPN, 802.1X wireless, dial-up Combines authentication and authorization in one exchange. Encrypts only the password, not the full payload. UDP-based. De facto standard for "is this user allowed onto the network?"
TACACS+ TCP 49 Device administration — switch/router CLI, firewall console Separates Authentication, Authorization, and Accounting (AAA). Per-command authorization. Encrypts the entire payload. TCP-based (reliable). Cisco-developed but supported widely.
LDAP / LDAPS TCP 389 / 636 Directory queries — looking up user attributes The protocol for talking to a directory service (Active Directory, OpenLDAP). Other auth methods (RADIUS, Kerberos, SAML) often use LDAP as the back-end identity store. LDAPS adds TLS.
Kerberos TCP/UDP 88 SSO inside an Active Directory domain Ticket-based. User authenticates once to get a TGT (Ticket-Granting Ticket), then uses it to request service tickets without re-entering passwords. Default for Windows AD logins. Time-sensitive — clocks must be within ~5 minutes.
SAML over HTTPS (443) Federation — SSO to SaaS apps and cross-org XML-based identity assertions passed between an Identity Provider (IdP — like Okta, Azure AD, ADFS) and a Service Provider (SP — like Salesforce, Workday). Browser redirects do the heavy lifting. The standard for SaaS SSO.
SSO varies Pattern, not a protocol "Sign in once, access many apps." Implemented via SAML, OIDC, Kerberos, or others depending on environment. Reduces password fatigue and centralizes audit. Requires MFA at the front door because one compromised SSO password = all apps compromised.
Local auth on-device Break-glass / device-only admin Credentials stored on the device itself, not a central server. Doesn\'t scale (can\'t reset 1000 device passwords easily). Use as fallback when central auth is unreachable. Audit and rotate regularly.
Need network access (VPN, Wi-Fi)?

RADIUS. Built for this exact use case. Add MFA for any admin/sensitive access.

Need device admin (router CLI)?

TACACS+. Better than RADIUS here because it supports per-command authorization and encrypts the whole session.

Need SaaS SSO (Salesforce, Workday)?

SAML. The dominant standard for cross-org SSO. OIDC is its modern JSON-based alternative.

Need Windows domain login?

Kerberos. Default for AD-joined machines. Make sure NTP is configured.

Need the user directory?

LDAP / LDAPS. The query protocol behind the scenes. AD speaks LDAP.

Need MFA?

Always. Layer it on whatever primary method you use. Password + phone push covers most cases.
